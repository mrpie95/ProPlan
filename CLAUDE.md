# ProPlan

ProPlan — single-file HTML/CSS/JS planning tool (also shipped as a Tauri macOS app). One product name everywhere: **ProPlan** (never "Carpati", never plain "Timeline" for the app; "Timeline" is only the name of a view). Plan, Timeline and other views run over the same state.

## File
- `ProPlan.html` — everything in one file. Open it directly in a browser, no build step.
- The tool is generic; the document title (`<project> — ProPlan`), About dialog and export defaults all say "ProPlan". The header has no brand/title text (the menu bar starts at the left edge). Legacy `carpati-timeline.*` localStorage keys are still migrated to `proplan.*` — keep that migration.

## Desktop app (Tauri)
- `src-tauri/` wraps the same HTML in a native macOS app shell — no separate frontend, no Rust logic. `scripts/tauri-prepare.mjs` copies `ProPlan.html` → `dist-tauri/index.html` (gitignored) before every dev/build run; that copy is the only "build step" involved.
- `npm run app:dev` — launch in a live dev window (re-run after editing the HTML; there's no file-watcher).
- `npm run app:build` — produces `src-tauri/target/release/bundle/macos/ProPlan.app` and a `.dmg`.
- The main window is created in `src-tauri/src/main.rs` (not `tauri.conf.json`) because it must register a download handler: WKWebView ignores `<a download>` / blob exports unless the host handles downloads. Files go to `~/Downloads`; the shell emits `proplan-download` and the page shows a toast with "Show in Finder" (`reveal_in_finder` command). `withGlobalTauri` is on so the single HTML can reach `window.__TAURI__`. Verified end to end by building with an injected auto-export and checking `~/Downloads`.
- CSP is disabled (`app.security.csp: null`) because the app loads html2canvas + jspdf from cdnjs at runtime for PNG/PDF export — those need internet access even inside the native app; everything else (state, snapshots, xlsx import/export) works fully offline via localStorage.
- App icon source: `src-tauri/icons/icon-source.png` (generated by `scripts/gen-icon.py`). Regenerate the full icon set with `npx tauri icon src-tauri/icons/icon-source.png` after swapping it.
- **Native menu bar** (`build_menu` in `src-tauri/src/main.rs`): ProPlan (About → the in-app dialog) · **File** · **Edit** · **View** · **Project** · Window — the SAME structure as the in-app `MENU_BAR` (see "Header: menu bar + navigation"). It only emits command ids; the page's `runCommand(cmd)` does the work (same ids as the in-app menu bar, `view:<id>` navigates). `tests/native-menu.test.mjs` fails if a menu id has no `runCommand` branch / unknown view — add the branch (or `BETA_VIEWS` entry) when adding a menu item.
- Bundle identifier `com.michaelpieniazek.proplan` — change in `src-tauri/tauri.conf.json` if this ever ships to someone else.

## Projects
- Several independent projects, each with its own saved state and its own snapshots. Registry in `proplan.projects`, open one in `proplan.activeProject`. The first project (`main`) uses the original keys (`proplan.v5`, `proplan.snapshots`), so pre-projects data is just "My project"; others use `proplan.v5.p.<id>` / `proplan.snapshots.p.<id>`.
- `STORAGE_KEY` / `SNAPSHOTS_KEY` are consts resolved once at boot from the active project. Switching projects (`switchProject`) reloads the page rather than swapping state in place — don't try to make it live.
- **Summary** tab (`renderSummary`, first tab): project name/dates, headline tiles, progress, per-product phases + launch, upcoming milestones, per-WP table, effort by discipline, snapshots/storage. All derived from `state` on render.
- Export / import live in **File ▸ Export ▸** and **File ▸ Import ▸** (see "Header: menu bar + navigation"); **Back up all projects…** is a File item. **Project as JSON** = plain state JSON (`<project>-<date>.json`); **Back up all projects** = `{format:"proplan-backup"}` with every project + snapshots; restoring a backup always ADDS projects (never overwrites). The one destructive import, **Project ▸ Replace plan from JSON…** (`import`), is kept apart from the safe ones.
- The project name at the right of the menu bar (`#projectBtnName`, clickable → `openProjectSwitcher`) opens **File ▸ Open project ▸**: the project list (switch / ✎ rename / 🗑 delete inline). New / Duplicate / Rename / Delete project, Save a copy as…, Import / Export and the desktop file items are in **File**; **Project** holds Process…, Save snapshot… / Snapshots…, Replace plan from JSON…, Load demo plan… and Clear timeline….
- **Never use native `confirm()` / `prompt()` / `alert()`.** The Tauri webview (WKWebView via wry) has no JS dialog support — confirm always returns false, prompt null, alert shows nothing. Use `uiConfirm` / `uiPrompt` / `uiAlert` (async, in-app modals; `await` them).

## Project files (desktop app)
- Each project is mirrored to `~/Documents/ProPlan/<slug>.proplan.json` = `{format:"proplan-project", version:1, savedAt, app:{version,build}, name, state, snapshots}`. localStorage stays the working copy; the file is the durable mirror. Pure helpers (tested in `tests/projectfiles.test.mjs`) live in `src/proplan-core.mjs` "Project files": `projectFileSlug`, `isSafeProjectFilename`, `uniqueProjectFilename`, `serializeProjectFile`, `parseProjectFile` (never throws; runs `normaliseState`; drops junk snapshots), `isFileNewerThanLocal`.
- Rust (`src-tauri/src/main.rs`, std::fs only): `project_dir`, `write_project_file` (temp + rename, atomic), `read_project_file` (confined to the folder), `list_project_files`, `rename_project_file`, `open_project_folder`; names must be bare `*.proplan.json` (no separators / `..`). The page calls them via `window.__TAURI__.core.invoke` (`pfInvoke`).
- HTML ("Project files (desktop app)" block after the project operations, `pf*` names): `saveState()` and `setSnapshots()` call `pfSchedule()` (debounced 400 ms, coalesced; flushed on hide/unload and before a project switch reload). One quiet toast per failure streak. Registry fields per project: `file`, `fileSavedAt`. Toggle `localStorage["proplan.fileSave"]` (default on in the app; off and invisible in a plain browser — menu items carry `desktop:true`). Status chip: Summary "Snapshots & storage" card + Project menu (`{t:"filestatus"}`).
- Menu ids: `openProjectFile` (chooser modal; always opens as a NEW project; asks via `uiConfirm` if the file already belongs to a project), `saveProjectCopy`, `showProjectFile`, `openProjectFolder`, `toggleFileSave`. Rename renames the file (`pfAfterRename`); deleting a project never deletes its file (the confirm says so).
- Startup (`pfStartup`): if the file's mtime is newer than the registry's `updatedAt`/`fileSavedAt` as they were at boot (`_PF_BOOT_META`), offer to load it (snapshot "Before loading from file" first); declining means the next save overwrites the file. Writes are held until this check ends.

## Processes (per-project phase model)
- A **Process** (`src/proplan-core.mjs`, "Processes" section) defines the phase model a project runs: `{id, name, description, doc, intro, phases[{code, name, summary, color{bg,accent,text}, num?, purpose?, deliverables?[], tasks?[]}], gates{enforce, label, finalLabel, finalCode}, entry, exit, commonDeliverables[], roles[]}`. `validateProcessDef` normalises it and derives `codes[]` + `order{code→index}`; processes are frozen.
- Built-ins: `sop18` (PRS → DP → DO → FP, the original behaviour, unchanged), `stagegate` (SCP → DEV → LCH, 3 phases, proves the abstraction), `none` (zero phases = phases off; replaces the old global "Phases (SOP-18)" toggle).
- Each project has `state.processId` (default/migration: missing or junk → `sop18`, done in `normaliseState`, so old exports/backups load as SOP-18; an unknown id is kept but resolves to `none` — `isProcessResolved(state)` is false and the UI says so; nothing is deleted).
- All phase functions read the process from state via `getProcess(stateOrProcess)` (omitted → SOP-18, so legacy call sites/tests are unchanged): `isBleedingBar(bar, proc?)`, `phaseSpanCodes(bar, proc?)`, `computePhaseGates(ranges, present, proc?)`, `computePhaseRanges`, `computeAllProductPhaseGates`, `enforcePhaseOrder` (no-op when `gates.enforce` is false or the process has no phases). `PHASE_ORDER` / `PHASE_CODES_IN_ORDER` remain exported as the SOP-18 constants. HTML helpers: `activeProcess()`, `procPhase(code)`, `phaseIdx(code)`, `isPhasesEnabled()` (= process has phases) — never hard-code phase codes in the UI.
- **Dormant tags:** a bar/lane/track phase code the active process doesn't know is ignored by every phase function (like untagged) but stays in state, so switching back restores it.
- **Switching** (`planProcessSwitch` dry run → `applyProcessSwitch`; UI `changeProcess()` in the HTML): shared codes keep their code, otherwise map by relative position (first→first, last→last, rest spread evenly; SOP-18→Stage-Gate = PRS→SCP, DP/DO→DEV, FP→LCH). Applies to `bar.phase`, `bar.phaseEnd` (dropped if the bleed no longer ends after its start), `lane.phase`, `track.activePhase` (+ legacy `state.activePhase`; `_closed`/null kept). Switching to `none` changes no tags. Dates are never moved (run Auto-sequence after). The UI shows the mapping via `uiConfirm`, saves a "Before switching to …" snapshot first, and Undo also reverts it.
- **Adding a process:** (built-in) add a `*_DEF` object next to `STAGEGATE_DEF`, `defineBuiltin()` it, add the id to `BUILTIN_PROCESS_IDS`, export it (and in `scripts/build.mjs` `EXPORT_NAMES`), add tests. (user-defined) `registerProcess(def)`; the HTML persists them under `localStorage["proplan.processes"]` via `serializeCustomProcesses()` / `loadCustomProcesses()` (no editor UI yet), and a project on a custom process embeds its definition in `state.processDef` so exports/backups stay self-contained (`normaliseState` re-registers it).
- UI: Project ▸ **Process…** (`changeProcess` → `openProcessPicker`; the native menu's old `togglePhases` id is kept as an alias for it), Summary-tab **Process** card, Process tab header + reference doc rendered from the active process (`renderProcess`; optional parts hidden when the process omits them). Tests: `tests/process.test.mjs`.

## Progress (completion checklist)
- **Progress** tab (`renderProgress`, second tab after Summary): every WP as a card with a header checkbox (marks all its tasks), progress bar, status chip and completed date; expand it for a status note (`lane.note`) and its task checkboxes, each with an editable completion date. Side column: "Completed over time" burn-up (SVG) and "Recent activity" feed (last 30 days, grouped by day). Tiles: WPs complete, tasks done, done in last 7 days, WPs finished in last 7 days, done-with-unknown-date. WP filter chips: All / Open / Complete.
- **Data:** `bar.done` + `bar.doneAt` (local `YYYY-MM-DD`; absent on ticks made before this existed → "date unknown", still counted). A WP is complete when it has ≥1 non-milestone task and all are done — derived by `laneProgress`, never stored. Milestones DO count (they are tickable: pending / done only, no in-progress). `state.log` is an append-only completion feed, capped at 500, entries carry label/WP-code snapshots so they survive deletions; `normaliseState` scrubs bad `done`/`doneAt`/`note`/`log` (old exports load with `log: []`).
- **Always mutate completion through core** — `setBarDone(state, barId, done, {now?, date?})`, `setLaneDone(state, laneId, done, …)`, `setLaneNote` — never `bar.done = …` directly, or `doneAt`/log drift. Re-dating an already-done bar moves its latest log entry too. The Timeline double-click toggle uses `Core.setBarDone`. Read side: `laneProgress`, `projectProgress`, `recentActivity`, `groupActivityByDay`, `completionSummary`, `completionSeries`. Tests: `tests/progress.test.mjs`.
- Ticking/dating/notes work in view-only mode (status updates, not structural edits). Reopening a whole WP asks via `uiConfirm`.

## Architecture
- Two views toggled by `<body data-view>`: `plan` (cards) and `timeline` (Monday-style table with sticky Phase | Task | Bars columns).
- `renderPlan()` builds the Plan view. `renderTimeline()` + `renderSingleBar()` build the Timeline view. Both read and write the same `state`.
- Dependencies are rendered as an SVG overlay inside the timeline grid (`renderArrows()`). Right-angle paths between bar centres, measured from the DOM (`getBoundingClientRect`) so arrows stay aligned even when lanes have variable height.
- Drag-to-connect: blue handle on each bar's right edge → `beginConnectDrag()`. Cycle detection in `createsCycle()`.
- Predecessor picker modal: `openDepEditor()`, used by both views.
- Auto-sequence: topological order via `topoOrder()`, sets each bar's `startIdx` to the latest finish of its predecessors. Spans preserved.

## Built-in preset
The old Carpati demo preset (`carpatiState()` / "Load Carpati WPs") no longer exists in the HTML; new projects start empty ("My project"). Test fixtures under `tests/fixtures/` still hold real-world plans.

## What's intentionally NOT in the timeline view
- Drag-on-empty-space to create a new bar — removed when we restructured to the Monday-style row-per-task layout (each task already has its own dedicated row, so empty space inside a track doesn't exist meaningfully). New tasks are added via the "+ Add task / deliverable" button at the bottom of each phase, or in Plan view.
- Internal bar labels and external-label overflow — task names now live in the dedicated Task column. Bars are clean coloured blocks. Tooltips on hover (via `title`) carry full info.

## Known limitations / things to revisit
- Phase header sticky-left positioning assumes `--phase-w: 170px` (constant `PHASE_W`). If you change `PHASE_W`, also update the `task-corner` / `task-cell` `left:` value.
- `applyStagger()` is dead code (was used when multiple bars shared a lane row). Safe to delete.
- `.bar .label`, `.bar .external-label`, `.bar.has-external` CSS rules are dead — bars no longer have internal labels. Safe to delete.
- The type group buttons in the header still set `activeType`, but `activeType` is unused now since drag-to-create is gone. Consider removing the type buttons or hooking them up to "+ Add task" so new tasks adopt the active type.
- Storage key has been bumped on every breaking schema change (v1 → v2 → v3). If the schema changes again, bump to v4 and add a migration or `normaliseState()` step.

## Conventions
- `lid()` for lane ids, `bid()` for bar ids — both random base36 short ids.
- Lane code follows `WP <n> — <short name>`. The renderer extracts `WP <n>` for compact display in dep chips. If you change this format, update the regex in the dep chip renderer.
- Phase colours cycle through `PHASE_PALETTE` (9 pastels). Add more if you exceed 9 phases regularly.

## HTML export (Confluence)
- File ▸ Export ▸ **Timeline as HTML (Confluence)…** (`runCommand("timelineHtml")` → `openTimelineHtmlExport()`, native menu has the same id) opens a **full-page view** (`.thx-page`, fixed over the app; Esc / ← Back closes): a large live preview of the export (iframe, `srcdoc`) beside a property panel that reuses the Timeline View card's look (`.vc-*` CSS is shared via `:is(#atPanelView, #thxPanel)`) — sections Output (Fragment / Full page, title), **Zoom** (the Timeline's Zoom: Months stepper/field, presets 3·6·12·24·All·Fit, From month, **Trim to planned**, readout; state `tx.zoom` 0|N|"fit", `tx.from`, `tx.trim`, mapped in `thxOptions` to `range: custom/planned`), Show (Track, Work package, Timeline filters), Display (Today, Milestones, Compact, Hover), Dependencies (Lines = routes, Pills), Milestones & names (With tasks / Bottom / Packed β, packed Names|Numbers, left-list names), Settings (Match Timeline, Reset); top bar has Copy HTML / Download .html. Settings are seeded from the Timeline's current ones (`thxSeed`), independent of them, and remembered in `proplan.thx` (`thxLoad`); `thxOptions(tx)` maps them to `exportTimelineHtml` options. Don't use a `<main>` element in such overlays — `body[data-view=altTimeline] main > :not(#altTimelineView)` hides it.
- **The export reproduces the Timeline tab** (light theme, tokens flattened to hex — keep it in step when the Timeline's look changes): dark year bar + month row, a 112px WP strip (muted WP-colour rail, "WPn" over the name) + a 66px ID/status-icon column with a light end-of-WP line, 22px rows / 18px blocks, ONE colour until started (blue → amber in progress → green done), buffer hatch, milestone diamonds, names inside a block only when the whole name fits (measured for the narrowest 900px table) otherwise beside it (flipped left near the right edge), one dependency pill per predecessor (green once it is done), a thin neutral Today line + pill and coloured launch lines + pills, matching legend. Option `names:true` puts task names in the left column. **Fixed pixel geometry:** the table is exactly `LABW + TRACK` px wide (`TRACK = max(900 − LABW, months × 52)`) everywhere it is pasted — a narrower page scrolls it, it never squeezes — and every x position, width, pill/label offset and buffer stripe is absolute px (no `%`, no `calc()`), so shapes never drift and the label-fit maths is exact. **Hover highlight:** option `hover:true` (modal checkbox, default on; core default off) prepends one small CSS-only `<style>` (`.pp-tl .pp-b/.pp-pill/.pp-row/.pp-wp` classes: block ring, row tint) — purely additive, so a host that strips `<style>` shows the identical chart. **Milestones at the bottom** (`milestonesAtBottom`, modal checkbox defaulting to the Timeline's setting): milestones leave their WPs (a WP of only milestones disappears) and form one "Milestones · N across all WPs" block at the end, sorted by date, each tagged `WPn` in the ID column and `WPn ·` before its name. **Range** (`range: "planned"|"custom"` + `rangeStart`/`rangeEnd` `YYYY-MM`; default whole project): `tlhRanged` re-bases a COPY of the state onto the first shown month (bars shifted by whole months, only in-range bars kept, partly-cut blocks clipped at the left edge, task codes/WP numbers taken from the original via the internal `_codes`) and exports that, so every geometry rule is unchanged; "planned" = first task start month → last task end month after the other filters, for projects that aren't fully planned. **Packed milestones (beta)** (`milestonesPacked`, `msNames` default true; modal "Pack milestones (beta)" / "Packed names", defaulting to the Timeline's settings; implies the bottom section): the milestone block uses shared rows — each milestone is a hexagon tag (SVG polygon, width from its code) holding the milestone code (`M3.2`), left tip + pin line + dot on the date, names (no WP prefix) beside it (to the left of the pin near the right edge) (or to its left near the right edge; the packer reserves that side) or are dropped for numbers-only (tooltip only). The ID column stays 66px. **Dependency routes** (`routes`, modal checkbox, default off; independent of the pills): one orthogonal path per visible link in an inline `<svg>` over the track (rows are a fixed `ROW` px, so y = row × ROW), coloured per predecessor, green once it is done, dashed when the successor starts before it ends. Status circles and the ID/WP tags are `flex:none` with fixed width+height (the ID column is 66px, 96px with milestones at the bottom) — Confluence's flex shrinking otherwise squashed them into ellipses. The legend lists only Not started / In progress / Done / Milestone / Buffer (no dependency entries; the pills stay in the chart). Tests assert these in `tests/htmlexport.test.mjs`.
- `exportTimelineHtml(state, opts)` in `src/proplan-core.mjs` ("HTML export") is pure: inline styles only, no script/link/resources (and no `<style>` unless `hover:true`); bars are percentage-positioned absolutes in fixed-height relative rows (tables can't place fractional months). opts `{mode, title, deps, showMilestones, compact, today, filterTrack, filterLane, shownBarIds}`; the UI passes `computeTimelineVisibility().shownBarIds`. Tests: `tests/htmlexport.test.mjs`.

- **Status tokens** (`/* ===== Status tokens ===== */` in the `:root` + dark blocks of the HTML): `--st-done|doing|pending` with `-border`, `-ink`, `-bg` variants (one green, one amber = in progress everywhere incl. Progress, grey = pending), plus `--control-border`. Use them instead of #22c55e/#16a34a/#f59e0b/#d97706 literals; `exportTimelineHtml` keeps literal hex (done #86efac/#15803d, doing #f59e0b) since it is self-contained. Timeline-tab bar rule: blocks are ONE colour (soft blue, `atBarColors`) until their status changes — in progress = amber fill, done = green fill (`.at-bar.is-doing/.is-done`); colour on this view therefore always means status. WP identity is only a muted 4px rail on the WP strip (`atWpColors` is the WP colour, used by the inspector chip and by Display ▸ Colour by WP, which brings per-WP pastels back for not-started blocks). One done indicator per row (the status circle). Dependency pills use `atDepColor` (6 muted cool hues, no green/amber/red) — EXCEPT a pill whose predecessor is done, which is green (`.at-jump.done`, fixed #15803d; `←` pills look at the listed predecessor, `→` pills at the block they hang off) and a link whose predecessor is done is never drawn as violated. Every predecessor/dependent gets its own pill — there is no "+N" collapse (`atExtPad` reserves 40px per predecessor for flipped labels).

## Global components, accessibility & naming
- **Control scale** (CSS section `/* ===== Control scale ===== */`, end of the stylesheet): buttons `--ctl-h-sm/md/lg` 24/28/36, pills `--pill-h-sm/md` 20/24, `--radius-ctl`, `--radius-pill`, `--mono` (IDs only). Legacy chip/button classes are mapped onto it there; use the tokens for new controls. Small clickable marks (`.ts-seg`, `.at-st`, `.wp-num-pill`, `.task-meta-chip`) get a 24px hit area via `::after`.
- One `:focus-visible` ring (2px accent, 2px offset) for all interactive elements; one disabled look (opacity .45, not-allowed); one Soon tag (`.soon-tag` / `.mi-tag`).
- **Icons:** `ICONS` map + `icon(name)` / `glyphIcon(emoji)` / `<span data-ico="name">` (auto-hydrated, also in dynamic HTML). Menu tables may keep emoji; `mbItemsHtml` maps them via `GLYPH_ICON`. No emoji in toolbars/menus.
- **Dialogs:** a MutationObserver adds a close button (`.modal-x`, dispatches Esc) and `aria-labelledby` to every `.modal`; headings are `h2/h3/.about-title` 16/700.
- **Naming:** Edit button = "Edit" / "Done" with an amber dot while editing (no EDITING pill); menu = "Edit mode"; nav dropdown button = "Views" (shows the open view name); panel toggle = "Panel"; cards "View" / "Inspector". Options-bar tool name hides below 1000px.
